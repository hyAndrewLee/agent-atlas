# Server conventions

- In a modular monorepo, group backend code by business capability (for example, orders and payments modules or packages). Keep the API entry point as the transport/composition host, not the owner of all business logic. Use the language's native modules, packages, exports, visibility, tests and build/workspace conventions to choose physical layout; no TypeScript file names, barrels, dunder directories or separate module manifest per capability are required.
- Within a capability, keep dependency direction transport adapters (routes/handlers: parsing, validation, authorization) → application/business operations (transport-independent rules) → owned persistence adapters. Keep operations cohesive and distinct, not one God service. A directory per operation can suit some stacks; in Go, cohesive use-case files in one capability package may be better than dozens of tiny packages. Keep private helpers and tests with their nearest owner in the language's idiom. Promote genuinely reused helpers to the nearest common owner without introducing a global shared-business-logic bucket.
- Make each service operation a thin, readable top-down sequence of explicitly named functions for cohesive domain tasks, with explicit inputs/outputs and independently testable behavior. Name steps for what they do (for example, load order context, check business rules, calculate totals, persist order), not generic pipeline stages. Avoid a monolithic service body, hidden mutable pipeline context, mandatory fluent chains/frameworks, and dozens of trivial one-line wrappers. Keep steps in the operation's owner or a native capability package as idiomatic; do not require a package, class or interface per step.
- Run dependent steps only after the preceding step succeeds. On failure, stop and propagate the language-native error/result (including cancellation), preserving its original cause and meaningful domain errors; at a useful operation boundary add the operation and failed-step context without replacing the cause with a generic error, logging at every layer, logging secrets, or ignoring failures. A step's single responsibility is not a separate database transaction: keep transaction/rollback integrity across the entire operation when required, rather than partially committing each step by default.
- Between capabilities, depend only on explicit public APIs and serializable contracts where needed, using native exported symbols/types/modules; do not import another capability's internals, repositories or ORM models or access its tables directly. Keep dependencies acyclic. Client-safe contracts must not pull in server secrets or database code. In-process calls can later gain transport adapters without making callers depend on transport details.
- A single process/deployment and physical database are fine now. Assign each capability ownership of its data and migrations; avoid cross-capability writes and hidden shared transaction coupling. Do not require queues, DI frameworks, speculative interfaces, separate databases, distributed transactions or network calls before they solve an actual problem.
- Consider extraction when measured load calls for independently scaling a hot capability. Extraction still needs explicit auth, errors/timeouts, consistency/transactions and deployment decisions; moving a directory alone is not a safe microservice migration.
