# Client conventions

- Follow the framework's layout convention where one applies. Define each layout in its own standalone file, separate from `page.tsx`; it may live in the page-owned layouts directory or be colocated as the framework permits. Never define a visual or route layout inline within `page.tsx`. In Next App Router, every page directory has its own `layout.tsx` alongside `page.tsx` (in addition to the required root layout); this colocated `layout.tsx` remains reserved for the automatic route layout. The automatic route `layout.tsx` owns its route shell and wraps `children` in the page-scoped client context provider once, including for static pages; it does not add the visual container. Next automatically renders the page as those children; do not import or invoke the route layout in the page. Layouts persist across navigation within their segment; do not rely on remounting for per-render resets. Keep layout and page server components unless genuinely client-only behavior requires otherwise; never call useContext or attach click handlers in a server component. Other frameworks use their appropriate layout equivalent, not Next-specific files.
- Keep each page/feature's focused business hooks in its own `__hooks__/` directory, one hook per file (for example, `orders/__hooks__/useOrders.ts` and `orders/__hooks__/useCart.ts`), with hook tests in `orders/__hooks__/__tests__/useOrders.test.ts` and nontrivial private helpers in `orders/__hooks__/__utils__/`. Keep page-level tests in the page's `__tests__/` directory (for example, `orders/__tests__/orders.test.tsx`), never mixed into production directories or a global cross-feature tests bucket. Context composes these hooks and exposes their values/actions; don't accumulate business implementations in a giant provider. Hooks may use ordinary React hooks internally without being wrapped in context unnecessarily.
- NEVER pass state or actions/callbacks through page-specific component props, even one intermediate hop, whether provider-owned or component-local. Each page-specific client component reads shared page state/actions directly from its page-scoped context (or a focused context-consuming hook); do not receive or forward those values through page-specific intermediates. Keep private UI state local when it is not shared; do not force it into context solely to hold it. The only exception for value-bearing component props is a genuinely reusable, decoupled component with explicit public props: it must not import page context, page hooks or other page-specific dependencies. Calling something reusable does not make it so, and forwarding through it into a page-specific component still violates this rule. Ordinary `children`/composition slots and native element attributes/events bound in the same component (including component-local UI state) are not prop drilling; keep the standalone visual layout's `children` slot and the page's direct ordered composition intact. Do not duplicate the provider or turn the server page/layout into a context consumer.
- Put page-owned visual children and overlays in the page's `__components__/` directory (for example, `orders/__components__/OrderSummary.tsx` and `orders/__components__/EditOrderDialog.tsx`); no per-component directory or barrel is required. Keep component-owned tests in `__components__/__tests__/` and nontrivial private helpers in `__components__/__utils__/` when needed; do not create empty directories. Promote helpers to a common owner only on actual reuse.
- Have `page.tsx` explicitly wrap focused visual children in a normal page-owned presentational layout component in its own file (for example, `orders/__components__/OrdersLayout.tsx` around five separate child lines), not a fragment or an inline layout function. This visual layout owns the outer styled container and arrangement (direction, gap, alignment, responsiveness); the page owns ordered composition and each child owns its internal styling. Do not put a raw outer styled container in the page, wrap the provider again, or import/invoke Next's automatic route layout as the visual wrapper. The visual layout is not a giant View or a second provider. Keep semantic DOM order aligned with visual reading order, without CSS `order` scrambling. A focused client child that opens an overlay (modal, dialog, sheet, drawer) owns its dynamic import, requested only when opened; do not eagerly mount hidden overlays or preload them. Server pages never handle click events. Preserve keyboard, focus management and accessible names.
