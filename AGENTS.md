# Ground rules

These are guidance for contributors and coding agents, not mechanically enforced checks. Apply the host tool's AGENTS.md scope and instruction precedence: this root section applies below its directory, more-specific applicable instructions refine it, and higher-priority instructions win. Apply framework-specific guidance only where that framework is in use; don't scaffold unrelated layers or pages.

Before editing project code, discover the conventions in the affected package/subsystem: read applicable ancestor and nested AGENTS.md instructions, relevant language/framework/package manifests and format/lint/build/test configuration, and a small representative set of nearby implementation and tests. Follow the project's established naming, file/package, API, error and test patterns when applying these rules; examples below are illustrative, not a mandate to reorganize existing code. Recheck applicable sources when entering a new scope or changing configuration. Higher-priority instructions and explicit scoped requirements take precedence; if a local convention conflicts with these rules or ambiguity materially affects the change, surface the concrete conflict rather than silently overriding or restructuring. No convention document or broad repository survey is required merely because a convention is not written down.

- Keep files cohesive rather than packing an entire feature into one file. Keep tests and nontrivial private helpers near their owner using the language's native test, package and visibility conventions; don't create empty directories or extract trivial helpers. Promote a helper only on demonstrated reuse to the nearest common owner, not a sibling feature or global bucket; update consumers' imports without crossing existing ownership boundaries. For JS/TS projects that use these conventions, put tests in the owner's `__tests__/` (for example, `features/invoice/__tests__/` or `features/invoice/__hooks__/__tests__/`) and private helpers in its `__utils__/`; reports and exports might share `features/__utils__/currency.ts`. These dunder paths are JS/TS examples, not requirements for other languages. In Go, tests normally sit beside implementation as `*_test.go`, and private helpers ordinarily stay in the owning package; Go tooling ignores directories beginning with `_`.
- For UI, pages, routing, client context, hooks, or overlays, read `.ground-rules/client.md` when relevant. For APIs, auth, business logic, persistence, or contracts, read `.ground-rules/server.md` when relevant. For mixed work read both; for unrelated work neither detailed document is needed. These are ordinary Markdown references, not automatically loaded instructions.
